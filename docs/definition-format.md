# Supported backend definition

The input is JSON with these required top-level keys:

```json
{
  "name": "Example API",
  "version": "0.1.0",
  "entities": [],
  "relationships": [],
  "apis": []
}
```

Use `examples/ecommerce.json` for a complete working example. Relationships must
currently be empty. Relationship generation, workflows, authentication, and
runtime/database customization are future features; unsupported settings are
rejected rather than silently ignored.

## Entities and fields

- Use PascalCase identifiers such as `User` or `OrderItem` for entities by convention.
- Fields use identifiers such as `id`, `createdAt`, or `display_name`. Identifiers
  start with a letter, contain letters/digits/underscores, and have at most 63
  characters. Reserved names and names that collide on Windows are rejected.
- Every entity has a `primaryKey` naming one of its fields.
- Integer primary keys are generated with auto-increment. String primary keys
  must be supplied by the client when creating a record.
- Field types: `string`, `integer`, `number` (Prisma Float), `boolean`, `date`,
  and `datetime` (both Prisma DateTime).
- Each field declares `required`, `unique`, and `nullable` booleans.
- `required` controls presence in create requests; `nullable` controls whether
  explicit `null` is allowed and whether the database column permits it.
- A nonrequired, nonnullable field needs a default so omitting it can succeed.
- `defaultValue` supports matching string, number, integer, and boolean values.
  Literal date defaults are not supported yet.
- `minLength` and `maxLength` apply to string fields.
- `autoGenerated: "createdAt"` and `"updatedAt"` apply to nonnullable date/datetime
  fields. These fields are managed by the database/ORM and cannot be edited through CRUD.

## APIs

Each API declares `name`, `method`, `path`, `entity`, and `operation`.

| Method | Operation | Path example |
| --- | --- | --- |
| GET | list | `/users` |
| POST | create | `/users` |
| GET | get | `/users/:id` |
| PUT | update | `/users/:id` |
| DELETE | delete | `/users/:id` |

Item routes must contain exactly the named primary-key parameter. Other dynamic
parameters, wildcards, custom Express route syntax, PATCH, and custom operations
are not yet supported. Method/path pairs must be unique. `GET /health` is reserved.

Only APIs declared in `apis` are exposed; declaring an entity does not automatically
expose all five operations. PUT currently accepts partial updates; it does not
replace the entire record.

## Request and response behavior

- Create bodies contain writable fields plus a string primary key, if used.
  Auto-increment IDs and generated timestamps must be omitted.
- Update bodies contain at least one writable field; primary keys and generated
  timestamps cannot be changed.
- Unknown body properties are rejected instead of silently dropped.
- Integer values fit PostgreSQL's signed 32-bit `Int`. Integer URL IDs must be
  positive base-10 values; `abc`, `0`, `-1`, `1.5`, and `1e3` are rejected.
- Dates use `YYYY-MM-DD`. Datetimes use an ISO datetime with a timezone, such as
  `2026-10-30T10:00:00Z`. Responses serialize these as ISO timestamps.

| Situation | HTTP status |
| --- | --- |
| Record created | 201 |
| Record read/listed/updated | 200 |
| Record deleted | 204 |
| Invalid body or ID, empty update, malformed JSON | 400 |
| Record not found | 404 |
| Unique value already exists | 409 |
| JSON body exceeds parser limit | 413 |
| Unexpected server/database error | 500 |
| Health check cannot connect to database | 503 |

This prototype does not provide authentication, authorization, pagination,
transactions for workflows, or production deployment configuration.
